# Portable OMP and Claude Configuration Restore Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Restore a sanitized, portable subset of OMP and Claude preferences while preserving all unrelated local configuration and runtime state.

**Architecture:** Add two curated source files in the separate `utils` repository. Extend the workstation bootstrap with dedicated preference restore paths rather than symlinks: Claude settings are merged as JSON, and OMP preferences are applied to a staged OMP config root through `omp config set`, then atomically installed. Existing destinations are backed up first; malformed, unsafe, or unavailable inputs fail closed or produce manual follow-up without affecting unrelated bootstrap work.

**Tech Stack:** Bash, Python 3 standard library (`json`), OMP CLI, JSON, YAML generated by OMP, shell fixture tests.

- [ ] **Step 1: Add metadata rows and extend metadata preflight**

Append these rows to `references/config-sources.tsv` using the existing tab-separated schema:

```text
claude-preferences	ai/claude/settings.json	.claude/settings.json	json-merge	base
omp-preferences	ai/omp/preferences.json	.omp/agent/config.yml	omp-merge	base
```

Add `json-merge` and `omp-merge` branches to `preflight_mapping()` and keep the existing `preflight_configs()` loop as the single source of profile/platform selection. Each new branch must:

1. Require a non-empty source and call `validate_source`.
2. Call the new per-tool source validator.
3. Call `validate_destination` on the relative destination.
4. Reject an existing destination symlink with `UNSAFE` without following it.
5. Require an existing destination to be a regular file.
6. For an existing Claude destination, parse it as a JSON object before any action.
7. Call `validate_backup_target` when an existing destination will be replaced.

Do not put the preference records in a second hard-coded loop. The metadata rows must drive source, destination, and profile selection.

- [ ] **Step 2: Add Python-backed source validators**

Add a helper invoked by metadata preflight that accepts an ID and canonical source path. The Python validator must:

- Parse Claude JSON as an object and allow only `model`, `autoCompactEnabled`, `autoCompactWindow`, `tui`, `voice`, and `voiceEnabled`.
- Require `model` and `tui` to be strings, `autoCompactEnabled` and `voiceEnabled` to be booleans, `autoCompactWindow` to be a positive integer, and `voice` to be an object containing only boolean `enabled` and string `mode`; reject bytes, absolute paths, `~` paths, shell commands, credential-like key names, and credential-shaped values.
- Parse OMP JSON as an object whose keys exactly match the 14-key portable allowlist in the spec.
- Accept only JSON scalar or array values supported by `omp config set`; reject nested provider/model/credential/path/extension/MCP/session/storage keys.
- Emit a nonzero exit status and `invalid agent preference source <id>` on malformed or disallowed data.

Keep source validation independent from destination merge logic so malformed source tests fail before any backup or write.

- [ ] **Step 3: Implement atomic Claude merge**

Implement `merge_claude_preferences <source> <destination>` and dispatch it from the `json-merge` branch in `process_configs()`. Its invariants:

- If `claude` is unavailable during apply, print `FOLLOW_UP Claude Code: install/authenticate Claude Code, then rerun bootstrap.` and return success without writing.
- In dry-run, print `PLAN AGENT_CONFIG claude-preferences -> $HOME/.claude/settings.json` and a backup plan when the destination exists; do not create a staging file.
- Create a staging file in the destination parent directory, not an unrelated filesystem.
- Use Python `json.load` to copy the existing object or start an empty object, overwrite only the approved top-level source keys, and write deterministic JSON to the staging file.
- Preserve every destination key not in the allowlist.
- Atomically `mv` the staging file into the destination only after JSON serialization succeeds.
- Back up the existing destination before staging replacement.
- Remove the staging file on all failure paths.

- [ ] **Step 4: Dispatch preference modes from the existing config processor**

Add `json-merge` and `omp-merge` branches to `process_configs()`:

```bash
json-merge) merge_claude_preferences "$source" "$destination" || return 1 ;;
omp-merge) merge_omp_preferences "$source" "$destination" || return 1 ;;
```

The OMP function is introduced in the next step; keep the branch name and argument contract stable. Existing `symlink`, `manual-review`, and `local` behavior must remain unchanged. Metadata preflight runs before package installation, while the action branches run in the existing configuration action phase.

- [ ] **Step 5: Implement OMP staged application**
Before running the staged merge, extend the fixture `omp` shim from Task 1 so it reads `PI_CODING_AGENT_DIR`, preserves the staged config file, logs keys to `$OMP_LOG`, and exits nonzero when `OMP_CONFIG_SET_FAIL=1`. It must never write the live destination unless the staged root is the live root.

Implement `merge_omp_preferences <source> <destination>` as follows:

1. If `omp` is unavailable during apply, print `FOLLOW_UP OMP: install Oh My Pi, then rerun bootstrap.` and return success without writing.
2. In dry-run, print `PLAN AGENT_CONFIG omp-preferences -> $HOME/.omp/agent/config.yml` and a backup plan when the destination exists; do not invoke `omp config set`.
3. Create a temporary OMP config root in the destination parent filesystem.
4. If a live config exists, copy it into the temporary root; otherwise start empty.
5. For each validated dotted-key/value pair from `ai/omp/preferences.json`, run:

```bash
PI_CODING_AGENT_DIR="$staged_root" omp config set "$key" "$value"
```

6. If any command fails, remove the staging root, leave the live destination unchanged, and report `cannot stage OMP preferences`.
7. Confirm the staged `config.yml` exists and is a regular file.
8. Back up the existing destination before the atomic move, then move the staged file into `.omp/agent/config.yml`.
9. Preserve unknown existing configuration by staging from the existing file before applying curated keys.

Do not call `omp config set` against the live home config. Do not copy `.omp/agent` as a directory.
